# KnowledgeTree — SD Worx hackathon POC

> Find it. Understand it. Trust it. One living organigram per customer; every node owns its knowledge; every change has a name.

## Run it

```bash
pnpm install
pnpm dev
# open http://localhost:3000
```

Data lives in `data/db.json` (created from the seed on first run). The **Reset demo** button on the dashboard restores the seed data at any time.

## What is in the box

Sign in on `/login` by picking a person (mock single sign-on). Each person only sees the customers they are assigned to; this filters the customer list, the tree, search, the Teams bot and the Outlook add-in.

Customers: Nike EMEA, Van der Valk Hotels, VRT, ArcelorMittal, Basic-Fit. Each customer subscribes to SD Worx products (Payroll, Time & Attendance, HR Administration, ...) and every entity of that customer carries exactly those categories. Inside a category, documents created by SD Worx are kept apart from documents received from the customer.

| Route | What it shows |
| --- | --- |
| `/` | Search prompt over all your customers. The best match shows entity, category, origin, owner, version and the expert to ask |
| `/customers` | Your customers with generated monogram logos, search and filters (industry, country, product) |
| `/customers/nike` | Organigram (React Flow). Every entity card shows the fixed product categories with counts; clicking an entity unfolds its product nodes (Payroll, Time & Attendance, ...). Click a product node for that category, split into SD Worx documents and documents received from the customer |
| `/activity` | Changes across all customers you are assigned to, with an "only my changes" toggle and a customer filter |
| `/teams` | Mock Teams client: hover a message → **Save to KnowledgeTree**; mention **@KnowledgeTree** to ask the tree |
| `/outlook` | Mock Outlook with the KnowledgeTree add-in: detects the entity and files attachments as documents received from the customer |

Documents are real files: every seeded document exists as a PDF, Excel or Word file under `public/files` (generated by `scripts/generate_files.py` with reportlab, openpyxl and LibreOffice) with a PDF preview. Click **View** on any document to open it in the viewer and download the original. Uploads from the portal are stored under `data/uploads` and served through `/api/files`. Notes are markdown, written in a full-screen editor with toolbar and live preview. Company logos come from Wikimedia Commons (`public/logos`).

Branding follows the real SD Worx Ignite design system (cdn.sdworx.com/ignite): primary blue #006dd8, dark navy #001c52, logo red #f1002f and yellow #ffbe00, neutral greys, radius 4/8 px, Inter for body text and SD Worx Display for headings (loaded from the SD Worx CDN). Tokens are in `src/app/globals.css`; product categories live in `src/lib/catalog.ts`.

## 3-minute demo script

1. **Login**: pick Lena. She sees Nike and Van der Valk only.
2. **Search** (`/`): "payroll cutoff Nike Germany" → best match with entity, Payroll category, owner Jonas, version and the expert to call.
3. **Tree**: open Nike EMEA. Click Nike Deutschland GmbH: its four product nodes unfold. Click **Payroll**: two SD Worx notes and the Lohnsteuer registration received from the customer. Click **View** on the Lohnsteuer document to open the PDF and show **Download**. Open the cutoff note: it renders as markdown. **Edit note** opens the full-screen editor; change something, add a reason → version 3 under Lena's name. **Upload** a real file from your laptop to show it lands in the tree and opens in the viewer.
4. **Teams** (`/teams`): hover Sofie's message → **Save to KnowledgeTree** → suggested entity, category and origin → Save. Ask `@KnowledgeTree what is the payroll cutoff for Nike Germany?`.
5. **Outlook** (`/outlook`): Katrin Vogel's email; the add-in shows the entity and what the tree knows. **File attachment to this node** → lands under "Received from customer".
6. **Changes** (`/activity`): everything on Nike and Van der Valk, toggle "Only my changes". Sign out and sign in as Amélie: Nike is gone.

## Deploy on Google Cloud (Cloud Run)

The app ships as a single container (see `Dockerfile`). Cloud Run builds it from source and gives you a public HTTPS URL in a few minutes.

```bash
# one-time setup
gcloud auth login
gcloud config set project YOUR_PROJECT_ID
gcloud services enable run.googleapis.com cloudbuild.googleapis.com artifactregistry.googleapis.com

# deploy from this folder (builds the Dockerfile with Cloud Build, then deploys)
gcloud run deploy knowledgetree \
  --source . \
  --region europe-west1 \
  --allow-unauthenticated \
  --memory 1Gi \
  --min-instances 1
```

The command prints the service URL when it finishes. Re-run the same command to redeploy after changes.

Notes for the demo:

- `--min-instances 1` keeps one instance warm so the first click during the pitch is instant.
- Data lives in a JSON file inside the container. It is seeded on first start and survives while the instance runs, but it is reset when Cloud Run replaces the instance. That is fine for a demo; use **Reset demo data** in the sidebar before you start.
- Uploads are stored in the container as well and disappear with it. For a real deployment, swap `src/lib/db.ts` for Firestore or Cloud SQL and `data/uploads` for a Cloud Storage bucket.
- The demo documents in `public/files` are committed, so nothing has to be generated on the server.

Local container check:

```bash
pnpm docker:build
pnpm docker:run   # http://localhost:8080
```

## Stack

Next.js 16 (App Router, server actions), React 19, Tailwind 4, @xyflow/react + dagre for the organigram, lucide-react icons. No database needed for the POC; a JSON file plays that role.
